# Requirements Document

## Introduction

The modem-gateway feature introduces a new telephony provider type for Svarla that enables SMS and voice calls via a physical USB modem (e.g., Quectel EG25-G with UAC firmware). The provider consists of two components: a standalone Go binary running on a Raspberry Pi (or similar SBC/OpenWrt device) with a connected USB modem, and a corresponding provider implementation on the Svarla server. The Go binary connects outbound to Svarla over a persistent signaling WebSocket for control messages, and to the MediaBridge over an ephemeral per-call audio WebSocket for voice data. This replaces the existing ModemManager-based provider with a cleaner, portable architecture.

## Glossary

- **Modem_Gateway_Binary**: The standalone Go binary that runs on the Raspberry Pi or similar device, communicating with the USB modem via AT commands and streaming audio via ALSA/UAC.
- **Svarla_Server**: The Node.js backend application that manages telephony providers, routing, and client connections.
- **Signaling_WebSocket**: The persistent WebSocket connection from the Modem_Gateway_Binary to the Svarla_Server, used for identity/auth, SMS, call signaling, DTMF, USSD, and status reporting.
- **Audio_WebSocket**: The ephemeral per-call WebSocket connection from the Modem_Gateway_Binary to the MediaBridge at `/audio/{sessionId}`, carrying raw PCM 16-bit 16kHz mono audio.
- **MediaBridge**: The Go service that bridges audio between WebRTC clients and telephony providers via SIP or WebSocket.
- **Provider_Registry**: The Svarla service that manages multiple telephony provider instances, their configuration, and lifecycle.
- **Pairing_Secret**: A one-time secret generated by Svarla during provider creation, used by the Modem_Gateway_Binary to establish initial trust and exchange cryptographic keys.
- **Ed25519_Keypair**: An asymmetric key pair generated locally by the Modem_Gateway_Binary for ongoing authentication after initial pairing.
- **UAC**: USB Audio Class — the standard by which the modem exposes its audio interface as an ALSA sound device.
- **AT_Commands**: Hayes-compatible serial commands used to control the modem for SMS, voice calls, DTMF, USSD, and status queries.
- **URC**: Unsolicited Result Code — asynchronous notifications sent by the modem over the AT serial port (e.g., RING, +CMTI, +CLIP).

## Requirements

### Requirement 1: Provider Registration and Configuration

**User Story:** As a Svarla user, I want to register a modem-gateway provider so that I can use a physical USB modem for telephony.

#### Acceptance Criteria

1. WHEN a user creates a provider with type "modem-gateway", THE Provider_Registry SHALL accept a display name (1 to 100 characters) as the only required configuration field.
2. WHEN a modem-gateway provider is created, THE Svarla_Server SHALL generate a cryptographically random one-time Pairing_Secret of at least 32 bytes and a signaling WebSocket connection endpoint URL scoped to the new provider's ID.
3. WHEN a modem-gateway provider is created, THE Svarla_Server SHALL return the Pairing_Secret and connection endpoint URL in the creation response for configuration of the Modem_Gateway_Binary.
4. THE Provider_Registry SHALL validate that the provider type "modem-gateway" is recognized and that the display name is a non-empty string of at most 100 characters.
5. IF a user attempts to create a provider with an unrecognized type or an empty/over-length display name, THEN THE Provider_Registry SHALL reject the request with a validation error indicating which field failed.
6. WHEN a modem-gateway provider is removed, THE Provider_Registry SHALL delete the stored public key, invalidate the Pairing_Secret if unused, and close any active Signaling_WebSocket connections for that provider.
7. IF a user attempts to remove a modem-gateway provider that does not exist, THEN THE Provider_Registry SHALL return a not-found error.

### Requirement 2: Device Pairing and Authentication

**User Story:** As a user setting up a new modem gateway, I want a secure pairing flow so that only my authorized device can connect to my Svarla instance.

#### Acceptance Criteria

1. WHEN the Modem_Gateway_Binary connects for the first time with a valid Pairing_Secret, THE Svarla_Server SHALL accept the Ed25519 public key submitted by the Modem_Gateway_Binary and store it in the provider configuration.
2. WHEN the Svarla_Server stores the public key from initial pairing, THE Svarla_Server SHALL invalidate the one-time Pairing_Secret so it cannot be reused.
3. WHEN a paired Modem_Gateway_Binary reconnects, THE Svarla_Server SHALL issue a cryptographic challenge containing at least 32 bytes of cryptographically random data, and the challenge SHALL expire if not answered within 30 seconds.
4. WHEN the Modem_Gateway_Binary provides a valid signature for the challenge within the challenge expiry window, THE Svarla_Server SHALL authenticate the connection and transition it to the active state, permitting signaling message exchange.
5. IF the Modem_Gateway_Binary provides an invalid signature, a challenge response after the 30-second expiry window, or a Pairing_Secret that was already used or is older than 24 hours since generation, THEN THE Svarla_Server SHALL reject the connection with an authentication error and close the WebSocket connection.
6. WHEN a user triggers a "reset" action on a modem-gateway provider, THE Svarla_Server SHALL close any active Signaling_WebSocket connection for that provider, delete the stored public key, and generate a new Pairing_Secret.
7. IF the Modem_Gateway_Binary presents a valid Pairing_Secret for a provider that already has a stored public key, THEN THE Svarla_Server SHALL reject the pairing attempt with an error indicating the provider is already paired.
8. IF a connection attempt fails authentication, THEN THE Svarla_Server SHALL enforce a minimum 1-second delay before accepting another authentication attempt from the same provider to mitigate brute-force attacks.

### Requirement 3: Signaling WebSocket Protocol

**User Story:** As a developer, I want a well-defined signaling protocol between the Go binary and Svarla so that SMS, call control, DTMF, USSD, and status can be exchanged reliably.

#### Acceptance Criteria

1. THE Signaling_WebSocket SHALL use JSON text messages for all signaling communication between the Modem_Gateway_Binary and the Svarla_Server, where each message contains a `type` field identifying the message kind.
2. THE Signaling_WebSocket SHALL support the following message categories: authentication, SMS (send/receive), call signaling (initiate/answer/hangup/incoming), DTMF (send/receive), USSD (request/response), and status reporting, where each category is identified by a unique `type` string value.
3. WHEN the Signaling_WebSocket connection is lost, THE Modem_Gateway_Binary SHALL reconnect with exponential backoff starting at 1 second, doubling on each attempt, up to a maximum delay of 60 seconds, and SHALL continue retrying indefinitely until the connection is re-established.
4. WHEN the Signaling_WebSocket reconnects after a disconnection, THE Modem_Gateway_Binary SHALL re-authenticate using the Ed25519 challenge-response flow.
5. THE Svarla_Server SHALL send WebSocket ping frames at an interval of 30 seconds on the Signaling_WebSocket, and SHALL close the connection if no pong response is received within 60 seconds.
6. IF the Signaling_WebSocket receives a message that is not valid JSON or contains an unrecognized `type` value, THEN the receiving side SHALL ignore the message and continue processing subsequent messages without closing the connection.
7. IF the Modem_Gateway_Binary receives a request message over the Signaling_WebSocket that it cannot fulfill, THEN THE Modem_Gateway_Binary SHALL respond with an error message of the same category indicating the failure reason.

### Requirement 4: SMS Send and Receive

**User Story:** As a Svarla user, I want to send and receive SMS through my USB modem so that I can communicate via text messages.

#### Acceptance Criteria

1. WHEN the Svarla_Server requests an SMS to be sent, THE Modem_Gateway_Binary SHALL send the SMS via AT command (`AT+CMGS`) over the modem serial port and report the result (success including a message reference, or failure including an error reason) back over the Signaling_WebSocket within 60 seconds of issuing the command.
2. WHEN the modem receives an incoming SMS (detected via `+CMTI` URC), THE Modem_Gateway_Binary SHALL read the message via AT command, extract the sender number, recipient number, message body, and timestamp, and forward them to the Svarla_Server over the Signaling_WebSocket.
3. IF the `AT+CMGS` command does not complete within 60 seconds or returns a CMS ERROR, THEN THE Modem_Gateway_Binary SHALL report the send as failed with an error reason to the Svarla_Server over the Signaling_WebSocket.
4. WHILE the Signaling_WebSocket is disconnected, THE Modem_Gateway_Binary SHALL buffer received SMS notifications locally up to a maximum of 1000 messages, discarding the oldest message when the buffer is full.
5. WHEN the Signaling_WebSocket reconnects after an outage, THE Modem_Gateway_Binary SHALL deliver all buffered SMS notifications to the Svarla_Server in chronological order (oldest first).
6. WHEN the Svarla_Server receives an incoming SMS from the Modem_Gateway_Binary, THE Svarla_Server SHALL emit an `incoming_sms` TelephonyEvent with the messageId, sender (from), recipient (to), message body, and timestamp.

### Requirement 5: Voice Call Initiation and Control

**User Story:** As a Svarla user, I want to make and receive phone calls through my USB modem so that I can use my physical SIM for voice communication.

#### Acceptance Criteria

1. WHEN the Svarla_Server instructs the Modem_Gateway_Binary to initiate an outbound call, THE Modem_Gateway_Binary SHALL dial the number using the AT command (`ATD`) and report call state transitions (RINGING, ANSWERED, COMPLETED, FAILED, BUSY) over the Signaling_WebSocket as the modem signals them.
2. WHEN the Svarla_Server instructs the Modem_Gateway_Binary to initiate a call, THE Svarla_Server SHALL include the MediaBridge Audio_WebSocket URL (containing the session ID) in the call setup message.
3. WHEN an outbound call is answered by the remote party, THE Modem_Gateway_Binary SHALL open the Audio_WebSocket connection to the MediaBridge URL provided during call setup.
4. WHEN the modem detects an incoming call (RING URC and +CLIP), THE Modem_Gateway_Binary SHALL notify the Svarla_Server via the Signaling_WebSocket with the caller number.
5. WHEN the Svarla_Server instructs the Modem_Gateway_Binary to answer an incoming call, THE Svarla_Server SHALL include the MediaBridge Audio_WebSocket URL in the answer message.
6. WHEN the Modem_Gateway_Binary receives an answer instruction with a MediaBridge Audio_WebSocket URL, THE Modem_Gateway_Binary SHALL answer the call via AT command (`ATA`) and open the Audio_WebSocket connection to the provided URL.
7. WHEN the Svarla_Server instructs the Modem_Gateway_Binary to hang up, THE Modem_Gateway_Binary SHALL end the call via AT command (`ATH`), close the Audio_WebSocket connection, and report COMPLETED state over the Signaling_WebSocket.
8. WHEN the modem signals that the remote party has disconnected (NO CARRIER URC), THE Modem_Gateway_Binary SHALL close the Audio_WebSocket connection and report COMPLETED state over the Signaling_WebSocket.
9. IF an incoming call arrives while the Signaling_WebSocket is disconnected, THEN THE Modem_Gateway_Binary SHALL reject the call via AT command (`ATH`) so the caller receives a network-level rejection.
10. THE Modem_Gateway_Binary SHALL support only one concurrent voice call at a time.
11. IF the Modem_Gateway_Binary receives a call initiation or answer instruction while a call is already active, THEN THE Modem_Gateway_Binary SHALL reject the instruction and report a FAILED state with a reason indicating a call is already in progress over the Signaling_WebSocket.
12. IF the ATD or ATA command fails or the modem returns an ERROR response, THEN THE Modem_Gateway_Binary SHALL report FAILED state with the modem error reason over the Signaling_WebSocket and close any Audio_WebSocket connection that was opened for that call.

### Requirement 6: Voice Audio Streaming

**User Story:** As a Svarla user on a voice call, I want clear bidirectional audio between my phone app and the remote party so that I can have a conversation.

#### Acceptance Criteria

1. WHILE a voice call is active, THE Modem_Gateway_Binary SHALL capture audio from the modem's UAC ALSA device as PCM 16-bit 16kHz mono and send it as binary WebSocket frames of 640 bytes (320 samples, 20ms duration) to the Audio_WebSocket at 20ms intervals.
2. WHILE a voice call is active, THE Modem_Gateway_Binary SHALL receive binary PCM 16-bit 16kHz mono frames from the Audio_WebSocket and play them to the modem's UAC ALSA device.
3. THE Audio_WebSocket connection SHALL use the session ID in the URL path (`/audio/{sessionId}`) as the authentication mechanism, consistent with the existing MediaBridge audio WebSocket protocol.
4. WHILE the Audio_WebSocket connection is active, THE Modem_Gateway_Binary SHALL respond to ping frames from the MediaBridge with pong frames so that the MediaBridge can detect dead connections within 60 seconds.
5. WHEN the voice call ends (either party hangs up), THE Modem_Gateway_Binary SHALL close the Audio_WebSocket connection with a normal closure code and release the ALSA device within 1 second.
6. IF the Audio_WebSocket connection drops during an active call (no pong received within 60 seconds or a TCP error occurs), THEN THE Modem_Gateway_Binary SHALL hang up the modem call via AT command and report the disconnection to the Svarla_Server over the Signaling_WebSocket.

### Requirement 7: DTMF Support

**User Story:** As a Svarla user on a voice call, I want to send and receive DTMF tones so that I can interact with automated phone systems (IVR menus).

#### Acceptance Criteria

1. WHILE a voice call is active, WHEN the Svarla_Server sends a DTMF digit (one of 0-9, *, #, A, B, C, D) to the Modem_Gateway_Binary over the Signaling_WebSocket, THE Modem_Gateway_Binary SHALL transmit the tone using AT command (`AT+VTS`) and report the result (success or failure) back to the Svarla_Server over the Signaling_WebSocket.
2. WHEN the modem detects an incoming DTMF digit (via URC) during an active voice call, THE Modem_Gateway_Binary SHALL forward the digit to the Svarla_Server over the Signaling_WebSocket.
3. IF the AT+VTS command fails or times out within 5 seconds, THEN THE Modem_Gateway_Binary SHALL report the failure to the Svarla_Server over the Signaling_WebSocket with an error indication specifying the digit that failed to send.
4. IF the Svarla_Server sends a DTMF digit request while no voice call is active, THEN THE Modem_Gateway_Binary SHALL reject the request and report an error to the Svarla_Server over the Signaling_WebSocket indicating no active call.

### Requirement 8: USSD Support

**User Story:** As a Svarla user, I want to send USSD requests through my modem so that I can check prepaid balance, top up, and interact with carrier services.

#### Acceptance Criteria

1. WHEN the Svarla_Server sends a USSD request containing a USSD code string (up to 182 characters) to the Modem_Gateway_Binary, THE Modem_Gateway_Binary SHALL execute the USSD command using `AT+CUSD` and return the network response text over the Signaling_WebSocket.
2. WHEN a USSD session requires multiple interaction steps, THE Modem_Gateway_Binary SHALL forward each intermediate response to the Svarla_Server and accept follow-up inputs over the Signaling_WebSocket until the session is terminated by the network, cancelled by the Svarla_Server, or closed due to inactivity timeout.
3. IF the modem returns a USSD error, THEN THE Modem_Gateway_Binary SHALL report the error code and description to the Svarla_Server over the Signaling_WebSocket and consider the USSD session terminated.
4. IF no response is received from the modem within 30 seconds of issuing a USSD command or follow-up input, THEN THE Modem_Gateway_Binary SHALL report a timeout error to the Svarla_Server over the Signaling_WebSocket and cancel the pending USSD session on the modem.
5. WHEN the Svarla_Server sends a USSD cancel request, THE Modem_Gateway_Binary SHALL terminate the active USSD session on the modem using `AT+CUSD=2` and confirm cancellation to the Svarla_Server over the Signaling_WebSocket.

### Requirement 9: Status Reporting

**User Story:** As a Svarla user, I want to see the modem's signal strength, network registration state, and operator name so that I can monitor connectivity.

#### Acceptance Criteria

1. THE Modem_Gateway_Binary SHALL query the modem for signal strength (`AT+CSQ`), network registration status (`AT+CREG`), and operator name (`AT+COPS`) every 30 seconds and report the results to the Svarla_Server over the Signaling_WebSocket.
2. WHEN the Modem_Gateway_Binary first connects (or reconnects) to the Signaling_WebSocket, THE Modem_Gateway_Binary SHALL immediately send a status report before resuming the periodic 30-second reporting cycle.
3. WHEN the Svarla_Server receives a status report, THE Svarla_Server SHALL store the signal strength value, network registration state, and operator name as the latest status for the corresponding modem-gateway provider.
4. IF the modem fails to respond to a status query within 5 seconds, THEN THE Modem_Gateway_Binary SHALL report the last known values for the unresponsive fields and indicate that those values are stale.

### Requirement 10: Number Discovery and Reporting

**User Story:** As a Svarla user, I want the modem's phone number to be automatically discovered and reported to Svarla so that routing works without manual configuration.

#### Acceptance Criteria

1. WHEN the Modem_Gateway_Binary starts, THE Modem_Gateway_Binary SHALL attempt to read the SIM phone number via AT commands (`AT+CNUM`) and, if that returns no number, fall back to reading the number from local configuration.
2. WHEN the Modem_Gateway_Binary establishes (or re-establishes) the Signaling_WebSocket connection, THE Modem_Gateway_Binary SHALL report the discovered phone number in E.164 format to the Svarla_Server.
3. IF the Modem_Gateway_Binary cannot discover a phone number from either AT+CNUM or local configuration, THEN THE Modem_Gateway_Binary SHALL report a "number_unavailable" status to the Svarla_Server and THE Svarla_Server SHALL mark the provider as unable to receive routed calls or SMS until a valid number is reported.
4. WHEN the Svarla_Server receives the phone number from the Modem_Gateway_Binary, THE Svarla_Server SHALL associate the number with the modem-gateway provider for routing purposes, replacing any previously stored number for that provider.
5. THE Svarla_Server SHALL use the existing number-based routing logic (unchanged) to route calls and SMS to the modem-gateway provider.

### Requirement 11: Modem Resilience and Reconnection

**User Story:** As a user with a modem gateway running on a Raspberry Pi, I want the system to handle modem disconnections and USB reconnections gracefully so that service resumes automatically.

#### Acceptance Criteria

1. IF the USB modem is disconnected or becomes unresponsive (no valid response to AT commands within 10 seconds), THEN THE Modem_Gateway_Binary SHALL detect the loss and attempt to reconnect to the modem using exponential backoff retries starting at 2 seconds and capping at 60 seconds, retrying indefinitely until the modem is recovered or the binary is stopped.
2. WHEN the modem becomes available again (USB reconnection or recovery), THE Modem_Gateway_Binary SHALL reinitialize the AT serial port and UAC audio device and report "modem_connected" status to the Svarla_Server over the Signaling_WebSocket.
3. WHILE the modem is unavailable AND the Signaling_WebSocket is connected, THE Modem_Gateway_Binary SHALL report "modem_disconnected" status to the Svarla_Server once upon initial detection of the modem loss.
4. WHILE the modem is unavailable AND the Signaling_WebSocket is connected, THE Modem_Gateway_Binary SHALL buffer up to 100 SMS send requests from the Svarla_Server and execute them in order when the modem recovers, discarding any requests older than 24 hours.
5. IF the USB modem becomes unavailable during an active voice call, THEN THE Modem_Gateway_Binary SHALL close the Audio_WebSocket connection and notify the Svarla_Server of the call termination with a "modem_lost" reason over the Signaling_WebSocket.

### Requirement 12: Svarla Provider Interface Implementation

**User Story:** As a developer, I want the modem-gateway provider to implement the TelephonyProvider interface so that it integrates seamlessly with the existing call orchestration and routing.

#### Acceptance Criteria

1. THE ModemGatewayTelephonyProvider SHALL implement all methods of the `TelephonyProvider` interface and SHALL expose `providerId` as "modem-gateway".
2. WHEN `makeCall` is invoked on the provider with a `from` number, `to` number, and optional `sipUri`, THE ModemGatewayTelephonyProvider SHALL send a call initiation message over the Signaling_WebSocket to the connected Modem_Gateway_Binary (including the MediaBridge Audio_WebSocket URL) and SHALL return a `CallInitResult` containing the provider-assigned call ID and a null `clientToken`.
3. WHEN `endCall` is invoked on the provider with a call ID, THE ModemGatewayTelephonyProvider SHALL send a hangup message over the Signaling_WebSocket to the Modem_Gateway_Binary.
4. WHEN `answerCall` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL send an answer message (including the MediaBridge Audio_WebSocket URL) over the Signaling_WebSocket to the Modem_Gateway_Binary and SHALL return a `CallAnswerResult` with `success` true, a null `clientToken`, and a null `errorReason`.
5. WHEN `sendSms` is invoked on the provider with `from`, `to`, and `body` parameters, THE ModemGatewayTelephonyProvider SHALL send an SMS request over the Signaling_WebSocket to the Modem_Gateway_Binary and SHALL return an `SmsResult` containing the message ID, success status, and error reason (null on success).
6. WHEN `listNumbers` is invoked on the provider and the Modem_Gateway_Binary has reported a phone number, THE ModemGatewayTelephonyProvider SHALL return a single-element array containing that number with VOICE and SMS capabilities.
7. IF `listNumbers` is invoked and no phone number has been reported by the Modem_Gateway_Binary, THEN THE ModemGatewayTelephonyProvider SHALL return an empty array.
8. WHEN `getWebhookEndpoints` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL return an empty array.
9. WHEN `handleWebhook` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL return an empty object (modem-gateway does not use HTTP webhooks).
10. WHEN `start` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL begin accepting incoming Signaling_WebSocket connections from paired Modem_Gateway_Binary instances.
11. WHEN `stop` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL close all active Signaling_WebSocket connections, reject any pending operation promises, and release resources.

### Requirement 13: Legacy ModemManager Provider Removal

**User Story:** As a developer, I want to remove the legacy ModemManager provider code so that the codebase is clean and the modem-gateway replaces it entirely.

#### Acceptance Criteria

1. THE Svarla_Server SHALL remove the `modemmanager-telephony-provider.ts` file, its corresponding test file `modemmanager-telephony-provider.test.ts`, and all import statements referencing the ModemManager provider from other source files.
2. THE Svarla_Server SHALL remove the `modemmanager` entry from the provider config validation schemas and remove the exported `modemmanagerConfigSchema` along with its associated test cases.
3. THE Svarla_Server SHALL remove the `dbus-next` dependency from `package.json` and regenerate the lock file so that no D-Bus packages remain in the dependency tree.
4. THE Svarla_Server SHALL remove the `case 'modemmanager'` branch from the provider factory function so that an unknown-type error is raised if the type "modemmanager" is encountered at runtime.
5. IF existing database rows in the `providers` table have type "modemmanager", THEN THE Svarla_Server SHALL include a numbered migration (next sequential after 011) that deletes associated rows from the `numbers` table and then deletes the provider rows, with a `down` function that is a no-op.
6. WHEN all ModemManager-related files and references have been removed, THE Svarla_Server SHALL compile without errors using the existing `npm run build` command and pass the existing test suite using `npm run test`.

### Requirement 14: Go Binary Modem Communication

**User Story:** As a developer, I want the Go binary to communicate directly with the modem via AT commands so that there is no dependency on ModemManager or other system services.

#### Acceptance Criteria

1. THE Modem_Gateway_Binary SHALL open the AT serial port at a user-configured device path (defaulting to `/dev/ttyUSB2`) using 115200 baud, 8N1 framing, and communicate with the modem using Hayes-compatible AT commands.
2. THE Modem_Gateway_Binary SHALL NOT depend on ModemManager, NetworkManager, or any D-Bus service for modem communication.
3. THE Modem_Gateway_Binary SHALL parse URC notifications from the modem asynchronously, supporting at minimum: RING, +CLIP, +CMTI, +CUSD, +DTMF, and +CREG.
4. WHEN the Modem_Gateway_Binary opens the serial port, THE Modem_Gateway_Binary SHALL send an initialization sequence that disables echo (`ATE0`), enables verbose result codes, enables caller ID reporting, enables SMS arrival notifications, and configures SMS mode (text mode via `AT+CMGF=1` as the default, falling back to PDU mode if text mode is not supported by the modem).
5. IF an AT command does not receive a final result code (OK, ERROR, +CME ERROR, or +CMS ERROR) within 30 seconds, THEN THE Modem_Gateway_Binary SHALL treat the command as failed and report the timeout.
6. IF the serial port cannot be opened or becomes unreadable, THEN THE Modem_Gateway_Binary SHALL report a modem communication error and retry opening the port with periodic retries.
7. THE Modem_Gateway_Binary SHALL be portable to Linux environments including Raspberry Pi OS and OpenWrt without requiring additional system services beyond a working serial port and ALSA, compiled as a statically-linked binary with no CGo dependencies beyond ALSA.
