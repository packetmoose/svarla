# Requirements Document

## Introduction

The modem-gateway feature introduces a new telephony provider type for Svarla that enables SMS and voice calls via a physical USB modem (e.g., SIMCom SIM7600G-H). The provider consists of two components: a standalone Go binary running on a Raspberry Pi (or similar SBC/OpenWrt device) with a connected USB modem, and a corresponding provider implementation on the Svarla server. The Go binary connects outbound to Svarla over a persistent signaling WebSocket for control messages, and to the MediaBridge over an ephemeral per-call audio WebSocket for voice data. This replaces the existing ModemManager-based provider with a cleaner, portable architecture.

## Glossary

- **Modem_Gateway_Binary**: The standalone Go binary that runs on the Raspberry Pi or similar device, communicating with the USB modem via AT commands and streaming audio via the PCM audio serial port.
- **Svarla_Server**: The Node.js backend application that manages telephony providers, routing, and client connections.
- **Signaling_WebSocket**: The persistent WebSocket connection from the Modem_Gateway_Binary to the Svarla_Server, used for identity/auth, SMS, call signaling, DTMF, USSD, and status reporting.
- **Audio_WebSocket**: The ephemeral per-call WebSocket connection from the Modem_Gateway_Binary to the MediaBridge at `/audio/{sessionId}`, carrying raw PCM 16-bit 16kHz mono audio.
- **MediaBridge**: The Go service that bridges audio between WebRTC clients and telephony providers via SIP or WebSocket.
- **Provider_Registry**: The Svarla service that manages multiple telephony provider instances, their configuration, and lifecycle.
- **Pairing_Secret**: A one-time, short alphanumeric code (6-8 characters) generated by Svarla during provider creation, used by the Modem_Gateway_Binary to establish initial trust and exchange cryptographic keys. Designed to be easy to type manually (e.g., via SSH into a Pi).
- **Ed25519_Keypair**: An asymmetric key pair generated locally by the Modem_Gateway_Binary for ongoing authentication after initial pairing.
- **UAC**: USB Audio Class — the standard by which some modems (e.g., Quectel EG25-G) expose their audio interface as an ALSA sound device. Reserved for future optional backend support.
- **PCM_Audio_Port**: The USB serial port (ttyUSB) exposed by the modem dedicated to streaming raw PCM audio data during voice calls, enabled via `AT+CPCMREG=1`.
- **AT_Commands**: Hayes-compatible serial commands used to control the modem for SMS, voice calls, DTMF, USSD, and status queries.
- **URC**: Unsolicited Result Code — asynchronous notifications sent by the modem over the AT serial port (e.g., RING, +CMTI, +CLIP).
- **Configuration_File**: The YAML or TOML file read by the Modem_Gateway_Binary at startup, containing connection settings, modem options, and feature flags.
- **Passive_Registration_Mode**: The default mode in which the Modem_Gateway_Binary does not manage modem network registration, deferring to the host OS or external tools.
- **Self_Registration_Mode**: An optional mode in which the Modem_Gateway_Binary directly manages modem network registration and SIM PIN unlock via AT commands.
- **GSM-7**: The default 7-bit character encoding used for SMS messages, supporting Latin characters, digits, and common symbols; allows up to 160 characters per single SMS segment.
- **UCS-2**: A 16-bit Unicode encoding used for SMS messages containing characters outside the GSM-7 character set (e.g., non-Latin scripts, emoji); limits a single SMS segment to 70 characters.
- **Concatenated_SMS**: A multi-part SMS message that is split into multiple segments for transmission and reassembled by the receiving device into a single logical message, using a concatenation header to identify parts.
- **Delivery_Report**: A status notification sent by the mobile network back to the sender's modem indicating whether an SMS was successfully delivered to the recipient or failed.

## Requirements

### Requirement 1: Provider Registration and Configuration

**User Story:** As a Svarla user, I want to register a modem-gateway provider so that I can use a physical USB modem for telephony.

#### Acceptance Criteria

1. WHEN a user creates a provider with type "modem-gateway", THE Provider_Registry SHALL accept a display name (1 to 100 characters) as the only required configuration field.
2. WHEN a modem-gateway provider is created, THE Svarla_Server SHALL generate a one-time Pairing_Secret consisting of 6 to 8 case-insensitive alphanumeric characters and a signaling WebSocket connection endpoint URL scoped to the new provider's ID.
3. WHEN a modem-gateway provider is created, THE Svarla_Server SHALL return the Pairing_Secret and connection endpoint URL in the creation response for configuration of the Modem_Gateway_Binary.
4. THE Provider_Registry SHALL validate that the provider type "modem-gateway" is recognized and that the display name is a non-empty string of at most 100 characters.
5. IF a user attempts to create a provider with an unrecognized type or an empty/over-length display name, THEN THE Provider_Registry SHALL reject the request with a validation error indicating which field failed.
6. WHEN a modem-gateway provider is removed, THE Provider_Registry SHALL delete the stored public key, invalidate the Pairing_Secret if unused, and close any active Signaling_WebSocket connections for that provider.
7. IF a user attempts to remove a modem-gateway provider that does not exist, THEN THE Provider_Registry SHALL return a not-found error.

### Requirement 2: Device Pairing and Authentication

**User Story:** As a user setting up a new modem gateway, I want a secure pairing flow so that only my authorized device can connect to my Svarla instance.

#### Acceptance Criteria

1. WHEN the Modem_Gateway_Binary connects for the first time with a valid Pairing_Secret, THE Svarla_Server SHALL accept the Ed25519 public key submitted by the Modem_Gateway_Binary and store it in the provider configuration.
2. WHEN the Svarla_Server stores the public key from initial pairing, THE Svarla_Server SHALL invalidate the one-time Pairing_Secret so it cannot be reused.
3. WHEN a paired Modem_Gateway_Binary reconnects, THE Svarla_Server SHALL issue a cryptographic challenge containing at least 32 bytes of cryptographically random data, and the challenge SHALL expire if not answered within 30 seconds.
4. WHEN the Modem_Gateway_Binary provides a valid signature for the challenge within the challenge expiry window, THE Svarla_Server SHALL authenticate the connection and transition it to the active state, permitting signaling message exchange.
5. IF the Modem_Gateway_Binary provides an invalid signature, a challenge response after the 30-second expiry window, or a Pairing_Secret that was already used or is older than 24 hours since generation, THEN THE Svarla_Server SHALL reject the connection with an authentication error and close the WebSocket connection.
6. WHEN a user triggers a "reset" action on a modem-gateway provider, THE Svarla_Server SHALL close any active Signaling_WebSocket connection for that provider, delete the stored public key, and generate a new Pairing_Secret.
7. IF the Modem_Gateway_Binary presents a valid Pairing_Secret for a provider that already has a stored public key, THEN THE Svarla_Server SHALL reject the pairing attempt with an error indicating the provider is already paired.
8. IF a connection attempt fails authentication, THEN THE Svarla_Server SHALL enforce a minimum 1-second delay before accepting another authentication attempt from the same provider to mitigate brute-force attacks.

### Requirement 3: Signaling WebSocket Protocol

**User Story:** As a developer, I want a well-defined signaling protocol between the Go binary and Svarla so that SMS, call control, DTMF, USSD, and status can be exchanged reliably.

#### Acceptance Criteria

1. THE Signaling_WebSocket SHALL use JSON text messages for all signaling communication between the Modem_Gateway_Binary and the Svarla_Server, where each message contains a `type` field identifying the message kind.
2. THE Signaling_WebSocket SHALL support the following message categories: authentication, SMS (send/receive), call signaling (initiate/answer/hangup/incoming), DTMF (send/receive), USSD (request/response), and status reporting, where each category is identified by a unique `type` string value.
3. WHEN the Signaling_WebSocket connection is lost, THE Modem_Gateway_Binary SHALL reconnect with exponential backoff starting at 1 second, doubling on each attempt, up to a maximum delay of 60 seconds, and SHALL continue retrying indefinitely until the connection is re-established.
4. WHEN the Signaling_WebSocket reconnects after a disconnection, THE Modem_Gateway_Binary SHALL re-authenticate using the Ed25519 challenge-response flow.
5. THE Svarla_Server SHALL send WebSocket ping frames at an interval of 30 seconds on the Signaling_WebSocket, and SHALL close the connection if no pong response is received within 60 seconds.
6. IF the Signaling_WebSocket receives a message that is not valid JSON or contains an unrecognized `type` value, THEN the receiving side SHALL ignore the message and continue processing subsequent messages without closing the connection.
7. IF the Modem_Gateway_Binary receives a request message over the Signaling_WebSocket that it cannot fulfill, THEN THE Modem_Gateway_Binary SHALL respond with an error message of the same category indicating the failure reason.

### Requirement 4: SMS Send and Receive

**User Story:** As a Svarla user, I want to send and receive SMS through my USB modem so that I can communicate via text messages.

#### Acceptance Criteria

1. WHEN the Svarla_Server requests an SMS to be sent, THE Modem_Gateway_Binary SHALL send the SMS via AT command (`AT+CMGS`) over the modem serial port and report the result (success including a message reference, or failure including an error reason) back over the Signaling_WebSocket within 60 seconds of issuing the command.
2. WHEN the modem receives an incoming SMS (detected via `+CMTI` URC), THE Modem_Gateway_Binary SHALL read the message via AT command, extract the sender number, recipient number, message body, and timestamp, and forward them to the Svarla_Server over the Signaling_WebSocket.
3. IF the `AT+CMGS` command does not complete within 60 seconds or returns a CMS ERROR, THEN THE Modem_Gateway_Binary SHALL report the send as failed with an error reason to the Svarla_Server over the Signaling_WebSocket.
4. WHILE the Signaling_WebSocket is disconnected, THE Modem_Gateway_Binary SHALL buffer received SMS notifications locally up to a maximum of 1000 messages, discarding the oldest message when the buffer is full.
5. THE Modem_Gateway_Binary SHALL persist the SMS notification buffer to disk so that buffered messages survive a restart or reboot of the Modem_Gateway_Binary process.
6. WHEN the Signaling_WebSocket reconnects after an outage or restart, THE Modem_Gateway_Binary SHALL deliver all buffered SMS notifications (including those restored from disk) to the Svarla_Server in chronological order (oldest first).
7. WHEN the Svarla_Server receives an incoming SMS from the Modem_Gateway_Binary, THE Svarla_Server SHALL emit an `incoming_sms` TelephonyEvent with the messageId, sender (from), recipient (to), message body, and timestamp.
8. WHEN the Modem_Gateway_Binary persists the SMS buffer to disk, THE Modem_Gateway_Binary SHALL write the buffer to a file in the binary's data directory so that it is available after a process restart or system reboot.

### Requirement 5: Voice Call Initiation and Control

**User Story:** As a Svarla user, I want to make and receive phone calls through my USB modem so that I can use my physical SIM for voice communication.

#### Acceptance Criteria

1. WHEN the Svarla_Server instructs the Modem_Gateway_Binary to initiate an outbound call, THE Modem_Gateway_Binary SHALL dial the number using the AT command (`ATD<number>;` where the trailing semicolon indicates a voice call) and report call state transitions (RINGING, ANSWERED, COMPLETED, FAILED, BUSY) over the Signaling_WebSocket as the modem signals them.
2. WHEN the Svarla_Server instructs the Modem_Gateway_Binary to initiate a call, THE Svarla_Server SHALL include the MediaBridge Audio_WebSocket URL (containing the session ID) in the call setup message.
3. WHEN an outbound call is answered by the remote party, THE Modem_Gateway_Binary SHALL open the Audio_WebSocket connection to the MediaBridge URL provided during call setup.
4. WHEN the modem detects an incoming call (RING URC and +CLIP), THE Modem_Gateway_Binary SHALL notify the Svarla_Server via the Signaling_WebSocket with the caller number.
5. WHEN the Svarla_Server instructs the Modem_Gateway_Binary to answer an incoming call, THE Svarla_Server SHALL include the MediaBridge Audio_WebSocket URL in the answer message.
6. WHEN the Modem_Gateway_Binary receives an answer instruction with a MediaBridge Audio_WebSocket URL, THE Modem_Gateway_Binary SHALL answer the call via AT command (`ATA`) and open the Audio_WebSocket connection to the provided URL.
7. WHEN the Svarla_Server instructs the Modem_Gateway_Binary to hang up, THE Modem_Gateway_Binary SHALL end the call via AT command (`ATH`), close the Audio_WebSocket connection, and report COMPLETED state over the Signaling_WebSocket.
8. WHEN the modem signals that the remote party has disconnected (NO CARRIER URC), THE Modem_Gateway_Binary SHALL close the Audio_WebSocket connection and report COMPLETED state over the Signaling_WebSocket.
9. IF an incoming call arrives while the Signaling_WebSocket is disconnected, THEN THE Modem_Gateway_Binary SHALL reject the call via AT command (`ATH`) so the caller receives a network-level rejection.
10. THE Modem_Gateway_Binary SHALL support only one concurrent voice call at a time.
11. IF the Modem_Gateway_Binary receives a call initiation or answer instruction while a call is already active, THEN THE Modem_Gateway_Binary SHALL reject the instruction and report a FAILED state with a reason indicating a call is already in progress over the Signaling_WebSocket.
12. IF the ATD<number>; or ATA command fails or the modem returns an ERROR response, THEN THE Modem_Gateway_Binary SHALL report FAILED state with the modem error reason over the Signaling_WebSocket and close any Audio_WebSocket connection that was opened for that call.
13. IF voice capability is unavailable (due to modem or firmware limitations, voice being disabled in configuration, or the PCM audio serial port being unavailable), THEN the phone number reported to the Svarla_Server SHALL NOT include VOICE capability, and THE Modem_Gateway_Binary SHALL only report capabilities that are actually available on the device.

### Requirement 6: Voice Audio Streaming

**User Story:** As a Svarla user on a voice call, I want clear bidirectional audio between my phone app and the remote party so that I can have a conversation.

#### Acceptance Criteria

1. WHILE a voice call is active, THE Modem_Gateway_Binary SHALL capture audio from the modem's PCM audio serial port (enabled via `AT+CPCMREG=1`) as PCM 16-bit mono and send it as binary WebSocket frames of 640 bytes (320 samples, 20ms duration at 16kHz) to the Audio_WebSocket at 20ms intervals.
2. WHILE a voice call is active, THE Modem_Gateway_Binary SHALL receive binary PCM 16-bit 16kHz mono frames from the Audio_WebSocket and write them to the modem's PCM audio serial port.
3. THE Audio_WebSocket connection SHALL use the session ID in the URL path (`/audio/{sessionId}`) as the authentication mechanism, consistent with the existing MediaBridge audio WebSocket protocol.
4. WHILE the Audio_WebSocket connection is active, THE Modem_Gateway_Binary SHALL respond to ping frames from the MediaBridge with pong frames so that the MediaBridge can detect dead connections within 60 seconds.
5. WHEN the voice call ends (either party hangs up), THE Modem_Gateway_Binary SHALL close the Audio_WebSocket connection with a normal closure code and disable PCM audio via `AT+CPCMREG=0` within 1 second.
6. IF the Audio_WebSocket connection drops during an active call (no pong received within 60 seconds or a TCP error occurs), THEN THE Modem_Gateway_Binary SHALL hang up the modem call via AT command and report the disconnection to the Svarla_Server over the Signaling_WebSocket.

### Requirement 7: DTMF Support

**User Story:** As a Svarla user on a voice call, I want to send and receive DTMF tones so that I can interact with automated phone systems (IVR menus).

#### Acceptance Criteria

1. WHILE a voice call is active, WHEN the Svarla_Server sends a DTMF digit (one of 0-9, *, #, A, B, C, D) to the Modem_Gateway_Binary over the Signaling_WebSocket, THE Modem_Gateway_Binary SHALL transmit the tone using AT command (`AT+VTS`) and report the result (success or failure) back to the Svarla_Server over the Signaling_WebSocket.
2. WHEN the modem detects an incoming DTMF digit (via URC) during an active voice call, THE Modem_Gateway_Binary SHALL forward the digit to the Svarla_Server over the Signaling_WebSocket.
3. IF the AT+VTS command fails or times out within 5 seconds, THEN THE Modem_Gateway_Binary SHALL report the failure to the Svarla_Server over the Signaling_WebSocket with an error indication specifying the digit that failed to send.
4. IF the Svarla_Server sends a DTMF digit request while no voice call is active, THEN THE Modem_Gateway_Binary SHALL reject the request and report an error to the Svarla_Server over the Signaling_WebSocket indicating no active call.

### Requirement 8: USSD Support

**User Story:** As a Svarla user, I want to send USSD requests through my modem so that I can check prepaid balance, top up, and interact with carrier services.

#### Acceptance Criteria

1. WHEN the Svarla_Server sends a USSD request containing a USSD code string (up to 182 characters) to the Modem_Gateway_Binary, THE Modem_Gateway_Binary SHALL execute the USSD command using `AT+CUSD` and return the network response text over the Signaling_WebSocket.
2. WHEN a USSD session requires multiple interaction steps, THE Modem_Gateway_Binary SHALL forward each intermediate response to the Svarla_Server and accept follow-up inputs over the Signaling_WebSocket until the session is terminated by the network, cancelled by the Svarla_Server, or closed due to inactivity timeout.
3. IF the modem returns a USSD error, THEN THE Modem_Gateway_Binary SHALL report the error code and description to the Svarla_Server over the Signaling_WebSocket and consider the USSD session terminated.
4. IF no response is received from the modem within 30 seconds of issuing a USSD command or follow-up input, THEN THE Modem_Gateway_Binary SHALL report a timeout error to the Svarla_Server over the Signaling_WebSocket and cancel the pending USSD session on the modem.
5. WHEN the Svarla_Server sends a USSD cancel request, THE Modem_Gateway_Binary SHALL terminate the active USSD session on the modem using `AT+CUSD=2` and confirm cancellation to the Svarla_Server over the Signaling_WebSocket.
6. IF a USSD request is received while a voice call is active, THEN THE Modem_Gateway_Binary SHALL reject the request and report an error to the Svarla_Server over the Signaling_WebSocket indicating that USSD is not available during an active voice call.

### Requirement 9: Status Reporting

**User Story:** As a Svarla user, I want to see the modem's signal strength, network registration state, and operator name so that I can monitor connectivity.

#### Acceptance Criteria

1. THE Modem_Gateway_Binary SHALL query the modem for signal strength (`AT+CSQ`), network registration status (`AT+CREG`), and operator name (`AT+COPS`) every 30 seconds and report the results to the Svarla_Server over the Signaling_WebSocket.
2. WHEN the Modem_Gateway_Binary first connects (or reconnects) to the Signaling_WebSocket, THE Modem_Gateway_Binary SHALL immediately send a status report before resuming the periodic 30-second reporting cycle.
3. WHEN the Svarla_Server receives a status report, THE Svarla_Server SHALL store the signal strength value, network registration state, and operator name as the latest status for the corresponding modem-gateway provider.
4. IF the modem fails to respond to a status query within 5 seconds, THEN THE Modem_Gateway_Binary SHALL report the last known values for the unresponsive fields and indicate that those values are stale.

### Requirement 10: Number Discovery and Reporting

**User Story:** As a Svarla user, I want the modem's phone number to be automatically discovered and reported to Svarla so that routing works without manual configuration.

#### Acceptance Criteria

1. WHEN the Modem_Gateway_Binary starts, THE Modem_Gateway_Binary SHALL attempt to read the SIM phone number via AT commands (`AT+CNUM`) and, if that returns no number, fall back to reading the phone number from the `phone_number` field in the Go binary's configuration file.
2. WHEN the Modem_Gateway_Binary establishes (or re-establishes) the Signaling_WebSocket connection, THE Modem_Gateway_Binary SHALL report the discovered phone number in E.164 format to the Svarla_Server.
3. IF the Modem_Gateway_Binary cannot discover a phone number from either AT+CNUM or the `phone_number` field in the configuration file, THEN THE Modem_Gateway_Binary SHALL report a "number_unavailable" status to the Svarla_Server and THE Svarla_Server SHALL mark the provider as unable to receive routed calls or SMS until a valid number is reported.
4. WHEN the Svarla_Server receives the phone number from the Modem_Gateway_Binary, THE Svarla_Server SHALL associate the number with the modem-gateway provider for routing purposes, replacing any previously stored number for that provider.
5. THE Svarla_Server SHALL use the existing number-based routing logic (unchanged) to route calls and SMS to the modem-gateway provider.

### Requirement 11: Modem Resilience and Reconnection

**User Story:** As a user with a modem gateway running on a Raspberry Pi, I want the system to handle modem disconnections and USB reconnections gracefully so that service resumes automatically.

#### Acceptance Criteria

1. IF the USB modem is disconnected or becomes unresponsive (no valid response to AT commands within 10 seconds), THEN THE Modem_Gateway_Binary SHALL detect the loss and attempt to reconnect to the modem using exponential backoff retries starting at 2 seconds and capping at 30 seconds, retrying indefinitely until the modem is recovered or the binary is stopped.
2. WHEN the modem becomes available again (USB reconnection or recovery), THE Modem_Gateway_Binary SHALL reinitialize the AT serial port and PCM audio serial port and report "modem_connected" status to the Svarla_Server over the Signaling_WebSocket.
3. WHILE the modem is unavailable AND the Signaling_WebSocket is connected, THE Modem_Gateway_Binary SHALL report "modem_disconnected" status to the Svarla_Server once upon initial detection of the modem loss.
4. WHILE the modem is unavailable AND the Signaling_WebSocket is connected, THE Modem_Gateway_Binary SHALL immediately reject any outgoing SMS send requests or call initiation requests from the Svarla_Server with an error indicating the modem is unavailable, without buffering the requests.
5. IF the USB modem becomes unavailable during an active voice call, THEN THE Modem_Gateway_Binary SHALL close the Audio_WebSocket connection and notify the Svarla_Server of the call termination with a "modem_lost" reason over the Signaling_WebSocket.

### Requirement 12: Svarla Provider Interface Implementation

**User Story:** As a developer, I want the modem-gateway provider to implement the TelephonyProvider interface so that it integrates seamlessly with the existing call orchestration and routing.

#### Acceptance Criteria

1. THE ModemGatewayTelephonyProvider SHALL implement all methods of the `TelephonyProvider` interface and SHALL expose `providerId` as "modem-gateway".
2. WHEN `makeCall` is invoked on the provider with a `from` number, `to` number, and optional `sipUri`, THE ModemGatewayTelephonyProvider SHALL send a call initiation message over the Signaling_WebSocket to the connected Modem_Gateway_Binary (including the MediaBridge Audio_WebSocket URL) and SHALL return a `CallInitResult` containing the provider-assigned call ID and a null `clientToken`.
3. WHEN `endCall` is invoked on the provider with a call ID, THE ModemGatewayTelephonyProvider SHALL send a hangup message over the Signaling_WebSocket to the Modem_Gateway_Binary.
4. WHEN `answerCall` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL send an answer message (including the MediaBridge Audio_WebSocket URL) over the Signaling_WebSocket to the Modem_Gateway_Binary and SHALL return a `CallAnswerResult` with `success` true, a null `clientToken`, and a null `errorReason`.
5. WHEN `sendSms` is invoked on the provider with `from`, `to`, and `body` parameters, THE ModemGatewayTelephonyProvider SHALL send an SMS request over the Signaling_WebSocket to the Modem_Gateway_Binary and SHALL return an `SmsResult` containing the message ID, success status, and error reason (null on success).
6. WHEN `listNumbers` is invoked on the provider and the Modem_Gateway_Binary has reported a phone number, THE ModemGatewayTelephonyProvider SHALL return a single-element array containing that number with capabilities matching those reported by the Modem_Gateway_Binary (VOICE and/or SMS based on actual availability as determined by R5.13 and R14.8-9).
7. IF `listNumbers` is invoked and no phone number has been reported by the Modem_Gateway_Binary, THEN THE ModemGatewayTelephonyProvider SHALL return an empty array.
8. WHEN `getWebhookEndpoints` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL return an empty array.
9. WHEN `handleWebhook` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL return an empty object (modem-gateway does not use HTTP webhooks).
10. WHEN `start` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL begin accepting incoming Signaling_WebSocket connections from paired Modem_Gateway_Binary instances.
11. WHEN `stop` is invoked on the provider, THE ModemGatewayTelephonyProvider SHALL close all active Signaling_WebSocket connections, reject any pending operation promises, and release resources.

### Requirement 13: Legacy ModemManager Provider Removal

**User Story:** As a developer, I want to remove the legacy ModemManager provider code so that the codebase is clean and the modem-gateway replaces it entirely.

#### Acceptance Criteria

1. THE Svarla_Server SHALL remove the `modemmanager-telephony-provider.ts` file, its corresponding test file `modemmanager-telephony-provider.test.ts`, and all import statements referencing the ModemManager provider from other source files.
2. THE Svarla_Server SHALL remove the `modemmanager` entry from the provider config validation schemas and remove the exported `modemmanagerConfigSchema` along with its associated test cases.
3. THE Svarla_Server SHALL remove the `dbus-next` dependency from `package.json` and regenerate the lock file so that no D-Bus packages remain in the dependency tree.
4. THE Svarla_Server SHALL remove the `case 'modemmanager'` branch from the provider factory function so that an unknown-type error is raised if the type "modemmanager" is encountered at runtime.
5. IF existing database rows in the `providers` table have type "modemmanager", THEN THE Svarla_Server SHALL include a numbered migration (next sequential after 011) that deletes associated rows from the `numbers` table and then deletes the provider rows, with a `down` function that is a no-op.
6. WHEN all ModemManager-related files and references have been removed, THE Svarla_Server SHALL compile without errors using the existing `npm run build` command and pass the existing test suite using `npm run test`.

### Requirement 14: Go Binary Modem Communication

**User Story:** As a developer, I want the Go binary to communicate directly with the modem via AT commands so that there is no dependency on ModemManager or other system services.

#### Acceptance Criteria

1. THE Modem_Gateway_Binary SHALL open the AT serial port at a user-configured device path (defaulting to `/dev/ttyUSB2`) using 115200 baud, 8N1 framing, and communicate with the modem using Hayes-compatible AT commands. THE Modem_Gateway_Binary SHALL also open the PCM audio serial port (a separate ttyUSB device, auto-detected or user-configured) for voice audio streaming during calls.
2. THE Modem_Gateway_Binary SHALL NOT depend on ModemManager, NetworkManager, or any D-Bus service for modem communication.
3. THE Modem_Gateway_Binary SHALL parse URC notifications from the modem asynchronously, supporting at minimum: RING, +CLIP, +CMTI, +CUSD, +DTMF, and +CREG.
4. WHEN the Modem_Gateway_Binary opens the serial port, THE Modem_Gateway_Binary SHALL send an initialization sequence that disables echo (`ATE0`), enables verbose result codes, enables caller ID reporting (`AT+CLIP=1`), enables DTMF detection (`AT+DDET=1`), enables SMS arrival notifications (`AT+CNMI`), and configures SMS mode (text mode via `AT+CMGF=1` as the default, falling back to PDU mode if text mode is not supported by the modem).
5. IF an AT command does not receive a final result code (OK, ERROR, +CME ERROR, or +CMS ERROR) within 30 seconds, THEN THE Modem_Gateway_Binary SHALL treat the command as failed and report the timeout.
6. IF the serial port cannot be opened or becomes unreadable, THEN THE Modem_Gateway_Binary SHALL report a modem communication error and retry opening the port with periodic retries.
7. THE Modem_Gateway_Binary SHALL be portable to Linux environments including Raspberry Pi OS and OpenWrt without requiring additional system services beyond a working serial port, compiled as a statically-linked binary with no CGo dependencies.
8. THE Modem_Gateway_Binary configuration file SHALL include an option to disable voice support entirely; voice SHALL be considered disabled if: (a) the voice_enabled flag is explicitly set to false in the configuration file, (b) the modem or firmware does not support voice calls, or (c) the PCM audio serial port is unavailable or `AT+CPCMREG` is unsupported.
9. WHEN voice is disabled (by any of the conditions above), THE Modem_Gateway_Binary SHALL report only SMS capability to the Svarla_Server and SHALL reject any call initiation or answer instructions received over the Signaling_WebSocket with an error indicating voice is not available.

### Requirement 15: Go Binary Configuration File

**User Story:** As a user deploying the modem gateway on a Raspberry Pi or similar device, I want to configure the Go binary via a configuration file so that I can set connection details, modem options, and feature flags without recompiling or using environment variables.

#### Acceptance Criteria

1. THE Modem_Gateway_Binary SHALL read configuration from a file in YAML or TOML format at a path specified via a command-line argument (defaulting to `./modem-gateway.yaml` if no path is provided).
2. THE Modem_Gateway_Binary SHALL support a `--generate-config` command-line flag (or argument) that generates a default configuration file at the configured path (or the default path if none specified), prints a message to standard output indicating the user should edit the file, and exits with a zero exit code. This allows first-time setup without requiring the binary to attempt a full startup.
3. THE configuration file SHALL include fields for: Svarla connection endpoint URL, pairing secret (used only during initial setup), serial port device path (defaulting to `/dev/ttyUSB2`), phone number override in E.164 format (optional), voice enabled/disabled flag (defaulting to true), network registration mode flag (defaulting to false), SIM PIN (optional), PCM audio serial port device path (optional, for overriding auto-detection of the modem's audio ttyUSB port), `ca_cert` path to a custom CA certificate file in PEM format (optional), `tls_skip_verify` flag to disable TLS certificate verification (optional, defaulting to false), `log_level` controlling the minimum log severity (optional, defaulting to "info"), and `log_file` path to write logs to a file instead of standard output (optional).
4. IF the configuration file is present but contains invalid syntax or missing required fields, THEN THE Modem_Gateway_Binary SHALL print a descriptive error message identifying the issue and exit with a non-zero exit code.
5. THE Modem_Gateway_Binary SHALL treat the Svarla connection endpoint URL and serial port device path as required fields, and SHALL treat all other fields as optional with documented defaults.
6. IF the Modem_Gateway_Binary is started without `--generate-config` and no configuration file exists at the configured path, THEN THE Modem_Gateway_Binary SHALL print an error message suggesting the user run with `--generate-config` to create a default configuration file, and exit with a non-zero exit code.

### Requirement 16: Modem Network Registration Mode

**User Story:** As a user running the modem gateway on a minimal system without ModemManager or a network manager, I want the Go binary to optionally handle modem network registration so that the modem can connect to the cellular network without external tooling.

#### Acceptance Criteria

1. THE Modem_Gateway_Binary SHALL default to passive registration mode, in which the Modem_Gateway_Binary does NOT perform modem network registration commands (`AT+COPS`, `AT+CREG` management) and assumes the host OS handles cellular network registration and data connectivity.
2. WHEN the `network_registration` flag is set to true in the configuration file, THE Modem_Gateway_Binary SHALL take control of network registration by issuing `AT+COPS=0` for automatic operator selection and monitoring `AT+CREG` for registration state changes.
3. WHILE self-registration mode is enabled, WHEN the modem reports that the SIM requires a PIN (via `+CPIN: SIM PIN` response), THE Modem_Gateway_Binary SHALL unlock the SIM using the PIN value from the `sim_pin` field in the configuration file via `AT+CPIN=<pin>`.
4. IF self-registration mode is enabled and the SIM requires a PIN but no `sim_pin` is configured, THEN THE Modem_Gateway_Binary SHALL report an error to the Svarla_Server indicating that SIM unlock failed due to a missing PIN and SHALL NOT attempt to register on the network until the PIN is provided.
5. IF the SIM PIN is rejected by the modem (incorrect PIN response), THEN THE Modem_Gateway_Binary SHALL report the failure to the Svarla_Server and SHALL NOT retry the PIN to avoid locking the SIM card.

### Requirement 17: Experimental Provider Feature Flag

**User Story:** As a Svarla developer, I want to hide the modem-gateway provider behind a feature flag so that it does not appear to users until it is ready for general use.

#### Acceptance Criteria

1. THE Svarla_Server SHALL NOT include "modem-gateway" in the list of available provider types returned to the web UI for the "add provider" flow unless the environment variable `EXPERIMENTAL_PROVIDERS` is set to the string value "true".
2. WHEN `EXPERIMENTAL_PROVIDERS` is not set or set to any value other than "true", THE Svarla_Server SHALL exclude "modem-gateway" from the provider type selection options in the UI, while continuing to operate any existing modem-gateway providers already configured in the database.
3. IF a modem-gateway provider already exists in the database, THEN THE Svarla_Server SHALL start and operate that provider normally regardless of the `EXPERIMENTAL_PROVIDERS` environment variable value.
4. THE feature flag SHALL only control visibility of the modem-gateway type in the UI provider creation flow; API requests to create a modem-gateway provider SHALL be accepted regardless of the flag value.

### Requirement 18: Multi-part and Unicode SMS Handling

**User Story:** As a Svarla user, I want to send and receive long messages and messages with non-Latin characters so that SMS communication works correctly regardless of content or language.

#### Acceptance Criteria

1. WHEN the modem receives a multi-part (concatenated) SMS, THE Modem_Gateway_Binary SHALL reassemble all parts into a single complete message before forwarding it to the Svarla_Server over the Signaling_WebSocket.
2. WHEN the Svarla_Server requests sending an SMS longer than 160 GSM-7 characters (or 70 UCS-2 characters), THE Modem_Gateway_Binary SHALL handle message splitting as required by the modem's capabilities (text mode handles this automatically; PDU mode requires explicit concatenation handling).
3. WHEN the message body contains characters outside the GSM-7 character set (non-Latin scripts, emoji, etc.), THE Modem_Gateway_Binary SHALL detect this and use UCS-2 encoding for the SMS transmission.
4. WHEN receiving an SMS encoded in UCS-2, THE Modem_Gateway_Binary SHALL decode it correctly and forward the full Unicode text to the Svarla_Server.

### Requirement 19: SMS Delivery Reports

**User Story:** As a Svarla user, I want to see when my sent SMS has been delivered so that I know the recipient received my message.

#### Acceptance Criteria

1. WHEN the Modem_Gateway_Binary sends an SMS, THE Modem_Gateway_Binary SHALL request a delivery report from the network (via `AT+CSMP` configuration or equivalent).
2. WHEN the modem receives an SMS delivery report (detected via `+CDS` URC or status report indication), THE Modem_Gateway_Binary SHALL forward the delivery status (delivered or failed) and the original message reference to the Svarla_Server over the Signaling_WebSocket.
3. WHEN the Svarla_Server receives a delivery report from the Modem_Gateway_Binary, THE Svarla_Server SHALL emit an `sms_status_update` TelephonyEvent with the messageId and status (DELIVERED or FAILED).

### Requirement 20: Call Duration Tracking

**User Story:** As a Svarla user, I want to see the duration of my calls so that I can track usage.

#### Acceptance Criteria

1. WHEN a voice call is answered (either inbound or outbound), THE Modem_Gateway_Binary SHALL record the timestamp of the answer event.
2. WHEN a voice call ends (COMPLETED state), THE Modem_Gateway_Binary SHALL calculate the call duration in seconds from the answer timestamp to the hangup timestamp and include the duration in the call_state_changed message sent to the Svarla_Server over the Signaling_WebSocket.
3. IF the call was never answered (FAILED or BUSY state), THEN THE Modem_Gateway_Binary SHALL report a null duration.

### Requirement 21: Missed Call Buffering

**User Story:** As a Svarla user, I want to be notified of calls that came in while my modem gateway was disconnected from Svarla so that I don't miss important calls.

#### Acceptance Criteria

1. IF an incoming call arrives while the Signaling_WebSocket is disconnected, THEN THE Modem_Gateway_Binary SHALL reject the call via AT command (`ATH`) and buffer a missed call notification locally containing the caller number and timestamp.
2. THE Modem_Gateway_Binary SHALL persist the missed call buffer to disk so that notifications survive a restart or reboot.
3. WHEN the Signaling_WebSocket reconnects after an outage or restart, THE Modem_Gateway_Binary SHALL deliver all buffered missed call notifications to the Svarla_Server in chronological order (oldest first).
4. THE missed call buffer SHALL share the same persistence mechanism and maximum size limits as the SMS buffer (up to 1000 entries, discarding the oldest when full).

### Requirement 22: TLS and Certificate Configuration

**User Story:** As a user deploying the modem gateway, I want to connect securely to my Svarla instance over TLS, including support for self-signed certificates, so that communication is encrypted.

#### Acceptance Criteria

1. THE Modem_Gateway_Binary SHALL connect to the Svarla Signaling_WebSocket using TLS (`wss://`) when the configured endpoint URL uses the `wss` scheme.
2. THE Modem_Gateway_Binary configuration file SHALL include an optional `ca_cert` field specifying the path to a custom CA certificate file (PEM format) used to verify the server's TLS certificate.
3. THE Modem_Gateway_Binary configuration file SHALL include an optional `tls_skip_verify` flag (defaulting to false) that, when set to true, disables TLS certificate verification (for development/testing with self-signed certificates).
4. WHEN connecting to the MediaBridge Audio_WebSocket, THE Modem_Gateway_Binary SHALL apply the same TLS configuration (custom CA or skip-verify) as used for the Signaling_WebSocket.

### Requirement 23: Logging and Diagnostics

**User Story:** As a user running the modem gateway on a headless device, I want configurable logging so that I can troubleshoot issues remotely.

#### Acceptance Criteria

1. THE Modem_Gateway_Binary SHALL support configurable log levels: error, warn, info, debug, and verbose.
2. THE Modem_Gateway_Binary configuration file SHALL include a `log_level` field (defaulting to "info") that controls the minimum severity of log messages output.
3. THE Modem_Gateway_Binary SHALL log to standard output by default, and SHALL support an optional `log_file` configuration field to write logs to a specified file path.
4. THE Modem_Gateway_Binary SHALL NOT log sensitive information (pairing secrets, private keys, SIM PINs, or message contents) at any log level except verbose, and SHALL redact such fields in log output at all other levels.
5. AT the verbose log level, THE Modem_Gateway_Binary SHALL log raw AT command exchanges with the modem (both commands sent and responses received) for debugging purposes.

### Requirement 24: Graceful Shutdown

**User Story:** As a system administrator, I want the modem gateway to shut down cleanly when stopped so that no data is lost and active calls are properly terminated.

#### Acceptance Criteria

1. WHEN the Modem_Gateway_Binary receives a SIGTERM or SIGINT signal, THE Modem_Gateway_Binary SHALL initiate a graceful shutdown sequence.
2. DURING graceful shutdown, IF a voice call is active, THEN THE Modem_Gateway_Binary SHALL hang up the call via AT command (`ATH`), close the Audio_WebSocket, and notify the Svarla_Server of the call termination over the Signaling_WebSocket.
3. DURING graceful shutdown, THE Modem_Gateway_Binary SHALL flush the SMS and missed call buffer to disk before exiting.
4. DURING graceful shutdown, THE Modem_Gateway_Binary SHALL close the Signaling_WebSocket connection with a normal closure code.
5. THE Modem_Gateway_Binary SHALL complete the graceful shutdown sequence within 10 seconds; if the sequence has not completed within 10 seconds, the binary SHALL force-exit.

### Requirement 25: Modem and Firmware Version Reporting

**User Story:** As a Svarla user, I want to see modem model and firmware version information so that I can verify compatibility and troubleshoot issues.

#### Acceptance Criteria

1. WHEN the Modem_Gateway_Binary initializes the modem, THE Modem_Gateway_Binary SHALL query the modem model (`AT+CGMM`), manufacturer (`AT+CGMI`), and firmware version (`AT+CGMR`) and store the results.
2. WHEN the Modem_Gateway_Binary first connects (or reconnects) to the Signaling_WebSocket, THE Modem_Gateway_Binary SHALL include the modem model, manufacturer, and firmware version in the initial status report.
3. THE Svarla_Server SHALL store the modem information as part of the provider's status and make it available for display in the provider detail view in the web UI.

### Requirement 26: Audio Sample Rate Handling

**User Story:** As a user with a SIM7600 series modem, I want the Go binary to negotiate the best available PCM sample rate so that voice calls have optimal audio quality.

#### Acceptance Criteria

1. WHEN the Modem_Gateway_Binary initializes for voice support, THE Modem_Gateway_Binary SHALL attempt to set the PCM sample rate to 16kHz by issuing `AT+CPCMFRM=1`.
2. IF `AT+CPCMFRM=1` succeeds (OK response), THEN THE Modem_Gateway_Binary SHALL use 16kHz PCM (640 bytes per 20ms frame) for audio streaming and send frames directly to the Audio_WebSocket without conversion.
3. IF `AT+CPCMFRM=1` fails (ERROR response or unsupported), THEN THE Modem_Gateway_Binary SHALL fall back to 8kHz PCM (320 bytes per 20ms frame) and upsample captured audio from 8kHz to 16kHz before sending over the Audio_WebSocket, and downsample received 16kHz audio to 8kHz before writing to the PCM serial port.
4. THE Audio_WebSocket protocol SHALL always carry PCM 16-bit 16kHz mono audio regardless of the modem's PCM sample rate (the binary handles any necessary conversion locally).
5. WHEN the modem resets or is reinitialized, THE Modem_Gateway_Binary SHALL re-issue `AT+CPCMFRM=1` since the setting does not persist across modem reboots.

### Requirement 27: Provider Documentation Page

**User Story:** As a Svarla user or developer, I want a documentation page for the modem-gateway provider so that I can understand setup requirements, supported hardware, and configuration.

#### Acceptance Criteria

1. THE Svarla project SHALL include a documentation page for the modem-gateway provider covering: overview and architecture, supported modems (with the SIMCom SIM7600G-H as the primary reference, and Quectel EG25-G with UAC firmware mentioned as a future option), hardware setup requirements (Raspberry Pi, USB modem, SIM card), Go binary installation and configuration including the `--generate-config` flag for first-time setup, pairing flow walkthrough, and troubleshooting common issues.
2. THE documentation page SHALL note that the Svarla server must be running with `EXPERIMENTAL_PROVIDERS=true` to add a new modem-gateway provider via the web UI.
3. THE documentation page SHALL list the required modem firmware features: PCM audio over USB serial port (`AT+CPCMREG` support) and AT command interface accessibility.


### Requirement 28: Systemd Service Documentation

**User Story:** As a user deploying the modem gateway on a Raspberry Pi or similar Linux system, I want documentation with systemd service examples so that I can run the Go binary as a managed background service that starts on boot.

#### Acceptance Criteria

1. THE provider documentation (from R27) SHALL include a dedicated section on running the Modem_Gateway_Binary as a systemd service.
2. THE documentation SHALL include a complete, ready-to-use example systemd unit file (`.service` file) with inline comments explaining each directive, covering: service type, restart policy, user/group, working directory, ExecStart pointing to the binary with config path argument, and standard output/error logging to journal.
3. THE documentation SHALL include step-by-step instructions for installing the service: copying the unit file to `/etc/systemd/system/`, running `systemctl daemon-reload`, enabling the service with `systemctl enable`, and starting it with `systemctl start`.
4. THE documentation SHALL include examples of common systemd management commands: checking status (`systemctl status`), viewing logs (`journalctl -u`), restarting (`systemctl restart`), and stopping (`systemctl stop`).
5. THE systemd unit file example SHALL configure the service to restart automatically on failure with a 5-second delay, and SHALL set appropriate resource limits and security hardening options (e.g., `ProtectSystem=strict`, `PrivateTmp=true`, device access for the serial ports).

### Requirement 29: Cross-Platform Build and Release Integration

**User Story:** As a developer or user, I want the Go binary to be built for both amd64 and arm64 architectures as part of the release process so that I can deploy it on both x86 servers and ARM-based devices like Raspberry Pi.

#### Acceptance Criteria

1. THE Svarla project's build system SHALL produce statically-linked Modem_Gateway_Binary artifacts for both `linux/amd64` and `linux/arm64` architectures.
2. THE existing release workflow (GitHub Actions) SHALL be extended to build the Modem_Gateway_Binary for both target architectures and include the resulting binaries as release assets alongside the existing Svarla server artifacts.
3. THE release assets SHALL follow a naming convention that clearly identifies the architecture: e.g., `modem-gateway-linux-amd64` and `modem-gateway-linux-arm64`.
4. THE build process SHALL produce reproducible builds with version information embedded in the binary (git tag/commit hash and build date), queryable via a `--version` flag on the binary.
5. THE Go binary build SHALL NOT require CGO (no ALSA or other C dependencies), enabling straightforward static compilation and cross-compilation for arm64 from an amd64 build host without a cross-compilation toolchain.
