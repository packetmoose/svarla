# Requirements Document

## Introduction

This feature adds encrypted SIP support to the Svarla mediabridge component. The mediabridge will listen for TLS-encrypted SIP connections on port 5061 in addition to the existing unencrypted SIP on port 5060, and negotiate SRTP via SDES when offered by providers. This enables secure voice signaling and media transport for providers that require or support encrypted SIP (such as Vonage).

## Glossary

- **Mediabridge**: The Go-based server component that handles SIP signaling and RTP media bridging between telephony providers and WebRTC clients.
- **TLS_Listener**: The TLS-wrapped TCP listener on port 5061 that accepts encrypted SIP connections from providers.
- **Unencrypted_Listener**: The existing UDP and TCP listener on port 5060 that accepts unencrypted SIP connections.
- **Certificate_Manager**: The component responsible for loading, validating, and hot-reloading TLS certificates used by the TLS_Listener.
- **SDES_Negotiator**: The component that parses SRTP crypto attributes from SDP offers and generates corresponding crypto answers for SRTP key exchange.
- **Provider**: An external telephony service (such as Vonage or 46elks) that connects inbound to the mediabridge via SIP after receiving an NCCO or equivalent webhook instruction.
- **SDP**: Session Description Protocol, used within SIP INVITE messages to describe media capabilities including codec, transport, and encryption parameters.
- **SDES**: Session Description Protocol Security Descriptions, a key exchange mechanism for SRTP where crypto keys are carried in SDP attributes.
- **SRTP**: Secure Real-time Transport Protocol, providing encryption and authentication of RTP media streams.
- **Self_Signed_Certificate**: A TLS certificate generated by the mediabridge at startup when no externally-provided certificate is mounted.
- **sipsUri**: A SIP URI using the `sips:` scheme indicating TLS-encrypted SIP transport (e.g., `sips:session-id@host:5061`).
- **Control_API**: The HTTP API exposed by the Mediabridge that the Svarla_Server calls to create sessions and obtain SIP URIs.
- **Svarla_Server**: The TypeScript backend server responsible for call orchestration, NCCO construction, and provider interaction.
- **NCCO**: Nexmo Call Control Object, a JSON instruction set returned via webhook that tells Vonage how to route a call.
- **Provider_Config**: The per-provider configuration within the Svarla_Server that describes a provider's capabilities, including whether it supports encrypted SIP.
- **Server_Config**: The top-level Svarla_Server configuration containing server-wide settings such as `sip.tls`.

## Requirements

### Requirement 1: Dual-Port SIP Listening

**User Story:** As a system operator, I want the mediabridge to listen on both port 5060 (unencrypted) and port 5061 (TLS-encrypted) simultaneously, so that providers can connect using either transport based on their configuration.

#### Acceptance Criteria

1. WHEN the Mediabridge starts, THE Unencrypted_Listener SHALL accept SIP connections on port 5060 via both UDP and TCP.
2. WHEN the Mediabridge starts, THE TLS_Listener SHALL accept SIP connections on port 5061 via TLS-over-TCP using TLS version 1.2 or higher.
3. THE Mediabridge SHALL route SIP messages through the same call-establishment and SDP-handling logic, producing the same SIP response codes and call routing outcomes, regardless of whether they arrive on the Unencrypted_Listener or the TLS_Listener.
4. WHILE the Mediabridge is running, IF one listener encounters a socket-level error or stops accepting connections, THEN THE other listener SHALL continue accepting and processing new SIP connections without interruption.
5. IF the TLS_Listener fails to start due to a certificate error, THEN THE Mediabridge SHALL log the error and terminate startup.
6. IF the Unencrypted_Listener fails to bind to port 5060 at startup, THEN THE Mediabridge SHALL log the error and terminate startup.

### Requirement 2: TLS Certificate Loading

**User Story:** As a system operator, I want to mount a TLS certificate into the container at a configurable path, so that the mediabridge uses my trusted certificate for encrypted SIP connections.

#### Acceptance Criteria

1. WHEN the Mediabridge starts, THE Certificate_Manager SHALL read the TLS certificate and private key from file paths specified in the mediabridge configuration.
2. WHEN PEM-encoded certificate and key files exist at the configured paths and the private key corresponds to the certificate's public key, THE Certificate_Manager SHALL load them for use by the TLS_Listener.
3. IF the configured certificate file is missing or unreadable, THEN THE Certificate_Manager SHALL fall back to generating a Self_Signed_Certificate.
4. IF the configured key file is missing or unreadable, THEN THE Certificate_Manager SHALL fall back to generating a Self_Signed_Certificate.
5. IF the certificate file cannot be parsed as a valid PEM-encoded X.509 certificate, THEN THE Certificate_Manager SHALL fall back to generating a Self_Signed_Certificate and log an error message indicating the parse failure.
6. IF the private key does not correspond to the loaded certificate, THEN THE Certificate_Manager SHALL fall back to generating a Self_Signed_Certificate and log an error message indicating the key mismatch.
7. IF a Self_Signed_Certificate is generated, THEN THE Mediabridge SHALL log a warning message indicating that a self-signed certificate is in use.

### Requirement 3: Certificate Hot-Reload

**User Story:** As a system operator, I want the mediabridge to detect when the TLS certificate file changes on disk and reload it without restarting, so that automated certificate rotation (such as Let's Encrypt via Caddy) works seamlessly.

#### Acceptance Criteria

1. WHILE the Mediabridge is running, THE Certificate_Manager SHALL monitor the configured certificate and key files for changes by checking file modification times at an interval no greater than 30 seconds.
2. WHEN a change is detected on either the certificate file or the key file, THE Certificate_Manager SHALL wait at least 2 seconds for both files to stabilize before attempting to load the new certificate and key pair together.
3. WHEN the new certificate and key files are loaded, THE Certificate_Manager SHALL validate that the certificate and private key form a matching pair before accepting them.
4. WHEN a new certificate is loaded and validated successfully, THE TLS_Listener SHALL use the new certificate for all subsequent TLS handshakes within 5 seconds of validation completing.
5. WHILE a certificate reload is in progress, THE TLS_Listener SHALL continue serving existing connections using the previous certificate without interruption.
6. IF the new certificate file is unparseable, expired, or does not match the loaded private key, THEN THE Certificate_Manager SHALL log an error indicating the specific failure reason and continue using the previously loaded certificate.
7. IF only one of the certificate or key files is updated and the other remains unchanged after the stabilization period, THEN THE Certificate_Manager SHALL attempt to load the updated file paired with the existing counterpart and validate the combination.
8. WHEN a certificate is successfully reloaded, THE Certificate_Manager SHALL log an informational message confirming the reload including the new certificate's subject and expiry date.

### Requirement 4: Self-Signed Certificate Generation

**User Story:** As a developer, I want the mediabridge to generate a self-signed certificate when no certificate is provided, so that TLS is always available on port 5061 without manual certificate setup during development.

#### Acceptance Criteria

1. WHEN no certificate files are configured or present, THE Certificate_Manager SHALL generate a Self_Signed_Certificate at startup.
2. THE Self_Signed_Certificate SHALL be a valid X.509 certificate with the Extended Key Usage field set to Server Authentication and a Subject Alternative Name containing the DNS name "localhost" and the IP address 127.0.0.1.
3. THE Self_Signed_Certificate SHALL have a validity period of 365 days from the time of generation and use an ECDSA P-256 key pair.
4. WHEN a Self_Signed_Certificate is generated, THE Mediabridge SHALL log a warning stating that a self-signed certificate is in use and recommending mounting a trusted certificate for production.
5. WHEN the Mediabridge restarts and no certificate files are configured or present, THE Certificate_Manager SHALL generate a new Self_Signed_Certificate rather than reusing a previously generated one.

### Requirement 5: SRTP Negotiation via SDES

**User Story:** As a system operator, I want the mediabridge to accept and negotiate SRTP when a provider offers it in the SDP, so that media streams are encrypted end-to-end between the provider and the mediabridge.

#### Acceptance Criteria

1. WHEN an incoming SIP INVITE contains one or more `a=crypto` attributes in the SDP audio media section, THE SDES_Negotiator SHALL parse each offered crypto suite including its tag, crypto suite identifier, and key parameter.
2. WHEN one or more supported crypto suites are offered, THE SDES_Negotiator SHALL select the first supported suite in offer order, generate a unique cryptographic key, and include a corresponding `a=crypto` attribute in the SDP answer with the matching tag.
3. WHEN SRTP is successfully negotiated, THE Mediabridge SHALL use the RTP/SAVP media profile and encrypt all outgoing RTP packets and decrypt all incoming RTP packets using the negotiated SDES keys for the duration of the SIP session.
4. WHEN an incoming SIP INVITE does not contain any `a=crypto` attributes in the SDP offer, THE Mediabridge SHALL proceed with unencrypted RTP using the RTP/AVP media profile.
5. THE SDES_Negotiator SHALL support the AES_CM_128_HMAC_SHA1_80 crypto suite as the only supported suite.
6. IF the SDP offer contains only unsupported crypto suites, THEN THE Mediabridge SHALL reject the INVITE with a 488 Not Acceptable Here response.
7. IF an `a=crypto` attribute in the SDP offer is malformed or cannot be parsed, THEN THE SDES_Negotiator SHALL skip that attribute and continue evaluating remaining crypto attributes in the offer.
8. WHEN a SIP session using SRTP ends, THE Mediabridge SHALL discard the negotiated SDES key material for that session.

### Requirement 6: TLS Configuration

**User Story:** As a system operator, I want to configure the certificate file paths in the mediabridge configuration file, so that I can specify where certificates are mounted in the container.

#### Acceptance Criteria

1. THE Mediabridge SHALL support a configuration section for TLS with fields for the certificate file path and the private key file path.
2. WHEN the TLS configuration section is absent from the configuration file, THE Certificate_Manager SHALL use default paths of "/etc/mediabridge/tls/cert.pem" and "/etc/mediabridge/tls/key.pem".
3. WHEN the TLS configuration specifies file paths, THE Certificate_Manager SHALL use those paths to load the certificate and key.
4. THE Mediabridge SHALL support a configuration field for the TLS listen port with a default value of 5061.
5. IF the TLS listen port value is outside the range 1 to 65535 or is not an integer, THEN THE Mediabridge SHALL reject the configuration and terminate startup with an error message indicating the invalid port value.
6. IF a configured TLS certificate path or key path is an empty string, THEN THE Certificate_Manager SHALL treat it as absent and use the default paths.
7. IF the configured TLS listen port is the same as the configured SIP port, THEN THE Mediabridge SHALL reject the configuration and terminate startup with an error message indicating the port conflict.

### Requirement 7: Docker Port Exposure

**User Story:** As a system operator, I want both SIP ports exposed in the Docker configuration, so that I can control which transports are available by choosing which ports to forward.

#### Acceptance Criteria

1. THE Mediabridge Docker configuration SHALL expose port 5060 for UDP and TCP (unencrypted SIP).
2. THE Mediabridge Docker configuration SHALL expose port 5061 for TCP only (encrypted SIP over TLS).
3. WHEN port 5061 is not forwarded by the Docker host, THE TLS_Listener SHALL still bind and accept connections on port 5061 inside the container, remaining unreachable only from outside the Docker network.
4. IF port 5060 is not forwarded by the Docker host, THEN THE Unencrypted_Listener SHALL still bind and accept connections on port 5060 inside the container.

### Requirement 8: SIP Transport Indication in Logging

**User Story:** As a system operator, I want SIP log messages to indicate whether a connection arrived over TLS or unencrypted transport, so that I can verify providers are connecting securely.

#### Acceptance Criteria

1. WHEN a SIP INVITE is received, THE Mediabridge SHALL log the transport type as one of "UDP", "TCP", or "TLS", along with the SIP Call-ID of the session.
2. WHEN a SIP session is established over TLS with SRTP, THE Mediabridge SHALL log that the session is using encrypted signaling and encrypted media, including the SIP Call-ID.
3. WHEN a SIP session is established with TLS but without SRTP, THE Mediabridge SHALL log that the session is using encrypted signaling and unencrypted media, including the SIP Call-ID.
4. WHEN a SIP session is established without TLS, THE Mediabridge SHALL log that the session is using unencrypted signaling, along with the SIP Call-ID and the transport type used.
5. THE Mediabridge SHALL include a timestamp with at most 1-second resolution in each SIP transport log entry.

### Requirement 9: Secure SIP URI Selection for NCCO

**User Story:** As a system operator, I want the Svarla server to automatically choose between an encrypted or unencrypted SIP URI when building the NCCO, so that calls use encrypted SIP transport when the provider supports it, while retaining the ability to force unencrypted SIP for debugging or environments without valid TLS certificates.

#### Acceptance Criteria

1. WHEN the Svarla_Server creates a session via the Control_API, THE Control_API SHALL return both a `sipUri` field containing the unencrypted SIP URI (using the `sip:` scheme and the configured SIP port) and a `sipsUri` field containing the encrypted SIP URI (using the `sips:` scheme and the configured TLS port).
2. WHEN the Svarla_Server constructs an NCCO and the Provider_Config has `supportsSips` set to true and the Server_Config has `sip.tls` set to true (or defaulted to true), THE Svarla_Server SHALL use the `sipsUri` value as the SIP endpoint URI in the NCCO connect action.
3. WHEN the Svarla_Server constructs an NCCO and the Server_Config has `sip.tls` set to false, THE Svarla_Server SHALL use the `sipUri` value regardless of the provider's `supportsSips` setting.
4. WHEN the Svarla_Server constructs an NCCO and the Provider_Config has `supportsSips` set to false or absent, THE Svarla_Server SHALL use the `sipUri` value as the SIP endpoint URI in the NCCO connect action.
5. THE Provider_Config for the Vonage provider SHALL default `supportsSips` to true when the field is not explicitly configured.
6. THE Server_Config `sip.tls` field SHALL default to true when not explicitly configured.
7. THE Control_API response format SHALL remain backward-compatible by retaining the existing `sipUri` field and adding the `sipsUri` field as an additional field.
